# Phase 6N — PS7331 kernel userspace-surface index

Date: 2026-08-10
Scope: host-only static analysis; no device mutation
Target source: `firmware/extracted/PS7331-SOURCE-20250617`

## Executive result

The build-selected MT8183 4.4 tree, the MediaTek vendor tree, and the Amazon
device-driver tree now have a reproducible source index of userspace-facing
surfaces. The index contains **4,278 source markers in 343 files**:

| Scope | Markers |
|---|---:|
| Build-selected MT8183 kernel | 4,169 |
| MediaTek vendor tree | 92 |
| Amazon device tree | 17 |

These are review markers, not vulnerability counts. A marker only means that
the source contains an ioctl, procfs/sysfs/debugfs/device registration,
user-copy, or related access-control construct.

The result does not identify a new root path or a HOME-control path. Existing
runtime evidence still shows that the relevant production boundaries are
Unix-node permissions and SELinux, and that the inspected driver paths do not
call or feed PackageManager, ActivityManager, ActivityTaskManager, or HOME
resolution.

## Reproduction

The index is generated by a host-only script. It reads source text and never
invokes ADB or opens a device node:

```sh
python3 -m py_compile tools/scripts/index_phase6n_kernel_user_surfaces.py
python3 tools/scripts/index_phase6n_kernel_user_surfaces.py --dry-run
python3 tools/scripts/index_phase6n_kernel_user_surfaces.py \
  --output output/tables/phase6n-kernel-user-surfaces.csv
```

The scanner deliberately includes only:

```text
platform/kernel/mediatek/mt8183/4.4
platform/vendor/mediatek
platform/device/amazon
```

This avoids counting generic, emulator, and alternate `4.4_emc` copies as if
they were the selected PS7331 kernel.

## Source findings

### CMDQ

`drivers/misc/mediatek/cmdq/v3/cmdq_driver.c` contains:

- `cmdq_ioctl()` and `cmdq_ioctl_compat()` at lines 660–736;
- ioctl file-operation registration at lines 739–741;
- user-copy paths for register/DMA, metadata, results, task properties,
  readback, and engine flags at lines 225–291, 350, 521–523, 575, 610–640,
  and 652;
- `device_create(..., "mtk_cmdq")` at lines 864–865;
- read-only proc entries at lines 820–824;
- `log_level` and `profile_enable` sysfs attributes at lines 70–73.

The source does not show a `capable()` or UID check in this entry path. That
does not establish unrestricted access: the live device boundary is the node
mode plus SELinux. Existing evidence records the node as
`system:system`, `crw-r--r--`, with `u:object_r:mtk_cmdq_device:s0`; the
compatibility probe returned `-ENOTTY` and no malformed or state-changing
ioctl was sent.

Classification: **source surface confirmed; exploitability and framework edge
unconfirmed**. The existing count/length arithmetic observation remains a
host-only review candidate.

### ION

`drivers/staging/android/ion/ion.c` contains `ion_ioctl()` at lines 1478–1617,
including `ALLOC`, `FREE`, `SHARE/MAP`, `IMPORT`, `SYNC`, and custom callback
commands. The ioctl and compat handlers are registered at lines 1657–1658,
and the `ion` misc device is registered around lines 1920–1924.

The path has `copy_from_user()` and `copy_to_user()` but no source-level
caller UID/capability check in the reviewed function. The source finding is
not a proof of a memory-safety issue, and no ION ioctl was issued to the
physical tablet.

Classification: **source surface confirmed; runtime reachability and impact
unconfirmed**.

### GED

`drivers/misc/mediatek/gpu/ged/src/ged_main.c` contains:

- `ged_ioctl()` and compat handling at lines 271–330;
- ioctl registration at lines 342–344;
- input/command/output handling at lines 118–257;
- `/proc/ged` creation with mode `0644` at line 411.

The existing query-only physical probe covered telemetry queries and observed
no package, Binder, system-server, or HOME state change. Non-query bridge,
reset, DVFS, or write operations were not executed.

Classification: **read/query surface confirmed; launcher/root path disproved by
current data-flow and runtime evidence**.

### M4U

`drivers/misc/mediatek/m4u/2.4/m4u.c` contains `MTK_M4U_ioctl()` at lines
1577–2043, with MVA, cache-sync, DMA, port, monitor, and translation-fault
operations. The proc entry is created around line 2268; the misc-device branch
is conditionally disabled in the selected configuration.

This is a high-impact hardware/memory-management surface, not a safe launcher
experiment. No M4U ioctl or debug write was sent to the tablet.

Classification: **source surface confirmed; no safe PoC and no framework HOME
edge**.

### Amazon-specific drivers

- `platform/device/amazon/kernel/driver/amzn_idme.c:316-347` creates IDME
  proc entries, strips write bits, and gives the secure MAC entry a restricted
  mode/owner.
- `platform/device/amazon/kernel/driver/amzn_drv_test.c:747-781` parses a
  bounded test index from a proc write and dispatches an Amazon driver test;
  entries are created around lines 811–841.
- `platform/device/amazon/kernel/driver/amzn_logger.c:696-747` registers
  `metrics`/`vitals` with read/poll/release operations and no write/ioctl
  operation.
- `platform/device/amazon/kernel/driver/amzn_sign_of_life.c:255-265` exposes
  a read-only lifecycle proc entry.

Runtime evidence already shows IDME ordinary fields read-only, lifecycle access
denied under SELinux, logger nodes restricted to `root:log`, and no usable
`amzn_ld` attributes. No Amazon driver path in this scope reaches a framework
launcher writer.

Classification: **source and production boundary confirmed; no User-0 HOME or
root transition**.

### MediaTek connectivity drivers

The vendor tree contains Wi-Fi, Bluetooth, and FM ioctl/device paths, including
firmware/log user-copy operations. Their actual production reachability still
depends on device-node mode, init registration, and SELinux policy. They were
indexed for completeness, but no payload or device-node mutation was attempted.

Classification: **inventory only; runtime impact unknown**.

## Current-device read-only correlation

After reviewing the capture script, one new read-only capture was run against
the explicitly selected device. It did not read the consuming metrics/vitals
character devices and did not write procfs, sysfs, debugfs, package state, or
settings.

Capture directory:

```text
adb/phase6n/PHASE6N-KERNEL-RO-20260810-01/
```

Observed:

- ADB state was `device`; caller was UID 2000 `shell` in `u:r:shell:s0`.
- SELinux was `Enforcing`, `ro.debuggable=0`, verified boot was `green`, and
  the running kernel identified as `4.4.146+`.
- `/proc/ged` was present with mode `0644`; the existing read-only probe
  boundary remains telemetry/query-only for this project.
- IDME ordinary entries were read-only; `mac_sec` was `system:root` with
  mode `0400`.
- `/dev/metrics` and `/dev/vitals` were `root:log` character devices with
  mode `0640`; the capture intentionally did not read them.
- `amzn_ld` parameter directory existed but contained no listed parameter
  files in the captured shell view.
- `/sys/kernel/debug/ged` was visible as a debugfs directory, but the capture
  did not enumerate or write debug entries.
- HOME still resolved to `com.amazon.firelauncher/.Launcher` with priority 50.

The nonzero exit codes in the capture are expected permission/availability
results from individual probes, not a mutation or harness failure. The full
per-command stdout/stderr and hashes are preserved; no rollback was needed.

## Decision

**已證實：** the selected source contains many userspace-facing kernel
surfaces, including CMDQ, ION, GED, M4U, and Amazon-specific proc/misc paths.

**高可信推論：** for the current launcher objective, the relevant production
control boundary is still the Android framework/package-policy layer; these
driver surfaces do not provide a demonstrated route to it.

**待驗證：** exact runtime reachability of selected vendor connectivity nodes
and the CMDQ arithmetic candidate. Verification would require either a safe
read-only node inventory or an isolated lab model; it does not justify a
malformed ioctl.

**已排除：** this index does not support a driver-to-HOME, driver-to-PMS, or
driver-to-root claim.

**因風險拒絕測試：** CMDQ/ION/M4U malformed requests, DMA/readback payloads,
GED write/reset bridges, sysfs/module-parameter writes, debugfs writes, kernel
race/panic triggers, and any Root or partition operation.

## Next direction

The highest-value remaining work is a host-only caller-to-sink closure for the
ordinary-app-reachable Amazon services and the OTA helper user-scope. If that
does not produce a User-0 package/HOME writer, the project should return to the
launcher fallback track and measure the best reversible foreground workaround,
without reopening the already disproved component-disable or priority tests.
