# Hypotheses and Current Disposition

The Amazon custom-home branch is no longer only a hypothesis: it is a confirmed framework capability. Whether it is activated depends on the foreground app's metadata, receiver and permission; the tested normal path continued to standard HOME resolution.

The earlier `HOME-PREF-T02`/`T03` difference was collected while the keyguard was showing. The controlled unlocked `HOME-T14`/`T15`/`T16`/`HOME-PREF-T17` runs all reached Fire, so keyguard is the current supported explanation for the apparent difference.

| ID | Hypothesis | Status | Evidence / next check |
|---|---|---|---|
| H-001 | Fire Launcher is selected by standard HOME resolution using its declared priority 50. | Confirmed for tested paths | Resolver/query output, package filter, VDEX `chooseBestActivity()`, and two logcat traces agree. |
| H-002 | The Home key bypasses the HOME resolver and directly launches Fire Launcher. | Disproved for tested ADB path | `startDockOrHome()` contains standard start path; ActivityManager logs resolved Fire component; no direct SystemUI launch found. |
| H-003 | Amazon added a Home-key/framework interception point. | Confirmed | `PhoneWindowManager.handleShortPressOnHome()` calls Amazon `KeyPolicyManager`; Fire OS XML registers the key-policy callback. |
| H-004 | Fire Launcher is selected by a persistent preferred activity. | Hypothesis not supported | Preferred record is present after `set-home-activity`, but no dedicated persistent HOME record is established; priority already explains selection. |
| H-005 | Fire Launcher is protected by a package watchdog that restores it after disable. | Disproved for `PACKAGE-T01` | PackageManager throws before state mutation. A boot-time watchdog may exist but is not needed for this failure. |
| H-006 | Amazon's protected-package callback is the vendor-specific reason shell cannot disable Fire Launcher. | Strong evidence | Runtime exception, framework callback path, Amazon registration and callback code agree; deny-list contents remain unreadable. |
| H-007 | SystemUI directly launches Fire Launcher on Home. | Disproved for inspected path | `SGObserver` references Fire Launcher only as the current foreground task, then explicitly launches Smart Genie; focused search found no direct Fire component launch. Copied framework classes limit the scope of this negative result. |
| H-008 | Settings removed the default-home implementation. | Disproved | `DefaultHomePreferenceController`, `DefaultHomePicker`, picker XML and resource boolean remain in Settings; the implementation is retained. |
| H-009 | A physical Home button follows the same path as `input keyevent 3`. | Hypothesis | Physical button has not yet been manually captured. |
| H-010 | An exact-match OTA will reveal additional launcher restrictions. | Hypothesis | Official PS7331 was acquired and extracted, but is marked `VERSION_MISMATCH` against PS7330.4104N; exact-build OTA evidence remains pending. |
| H-011 | The Microsoft-foreground `KEYCODE_HOME` exception is caused by Amazon's key-policy/custom-home branch. | Disproved for the tested condition | `HOME-PREF-T02` and `T03` show `mKeyguardShowing=true`; unlocked `HOME-PREF-T17` with the Microsoft preferred record starts Fire. A special branch in another keyguard or foreground condition remains a separate hypothesis. |
| H-012 | Amazon's LauncherHijackPreventer directly starts Fire Launcher on Home. | Disproved for inspected callback path | `canSeeHomeTask()` implements SELinux/signature-based Home-task visibility; no Fire component start appears in that method. Direct-launch claims require new evidence. |
| H-013 | The LauncherHijackPreventer is an Amazon framework policy modification. | Confirmed | Amazon `fosinit` registers the ActivityStack callback; ActivityStack invokes it for Home-task visibility; VDEX contains the `see_home_task` and signature checks. |
| H-014 | `cmd package disable-user` has a separate path that bypasses or weakens Fire Launcher protection. | Disproved | `PACKAGE-T05` reaches the same `PackageManagerService.setEnabledSetting()` protected-package exception as `PACKAGE-T03`/`pm`; the invalid `cmd disable-user` attempt in `PACKAGE-T04` is not a valid package command. |
| H-015 | Amazon's custom dock callback directly starts Fire Launcher in the ordinary tablet path. | Disproved for inspected callbacks | `PhoneWindowManager.startDockOrHome()` offers callbacks, but the inspected Alexa callback only starts a provider-supplied multimodal Home Intent for mode 1 and contains no Fire Launcher component. `HOME-T18`/`T19` reach Fire after the normal HOME start. |
| H-016 | The Alexa mode switch is observable as an active shell service and proves the custom direct-home branch ran. | Hypothesis not supported | `service list` names `alexa_modeswitch`, but `dumpsys` and `service call ... 2` fail and `mss_mode` is `null`; no activation claim is made. |
| H-017 | Amazon/Fire OS hides the main Default apps Home selector while retaining the underlying picker implementation. | Confirmed | Installed `app_default_settings.xml` omits `default_home`, while AOSP r1/r61 include it; `HOME-T21` shows no Home row, and controller/picker classes/resources remain. |
| H-018 | The Fire Launcher App info `Home app` row provides a direct no-root launcher picker. | Disproved for the tested route | `HOME-T23` taps only that row and reaches `com.android.settings/.SubSettings` Default apps; the resulting UI still has no Home row. Static controller code launches `DefaultAppSettings`, not `DefaultHomePicker` directly. |
| H-019 | `config_show_default_home=false` is the reason the Home selector is absent. | Disproved | Installed `decompiled/jadx/settings/resources/res/values/bools.xml:36` sets `config_show_default_home` to `true`; the observed omission is in `app_default_settings.xml`. |
| H-020 | The active parental-controls Profile Owner causes the `pm disable-user` Fire Launcher exception. | Disproved for the tested disable path | `POLICY-T01` confirms the Profile Owner and no effective user restrictions, while `PACKAGE-T01`/`T03`/`T05` terminate in `PackageManagerService.setEnabledSetting()` protected-package enforcement. The parental-controls APK uses `setApplicationRestrictions()` for Fire Launcher policy keys, not the tested package-enabled-state call. |
| H-021 | A parental-controls or boot watchdog generally re-enables Fire Launcher after shell disable. | Disproved for the tested failure; special-user behavior remains separate | The disable request fails before state mutation. The inspected parental package-change/boot receivers do not re-enable Fire; Amazon's KFT child-user path instead enables FreeTime Launcher and sets Fire Launcher state to `2` for that user. |
| H-022 | The retained `DefaultHomePicker` is reachable through a normal shell-visible Settings route. | Probable unavailable for tested routes | `SETTINGS-T01` is blocked by non-exported `SubSettings`; corrected `SETTINGS-T03` falls back to the metadata-selected Default apps dashboard. A privileged/internal caller was not exhaustively enumerated. |
| H-023 | Disabling only `com.amazon.firelauncher/.Launcher` can bypass package-level protection and expose another HOME candidate. | Disproved | `COMPONENT-T01` (`pm`) and `COMPONENT-T02` (`cmd package`) both return the protected-package exception from `setComponentEnabledSetting()`; `disabledComponents`, resolver and focus remain unchanged. |

The adjacent PS7331 observations are retained as cross-version evidence only. They support tool and class-path continuity but do not establish that the installed PS7330 build has identical bytecode.
