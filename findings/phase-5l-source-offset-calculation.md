# Phase 5L — public source and source-derived offset calculation

## Scope and safety boundary

This is a host-only source/ABI calculation. It does not extract a boot image,
read a partition, recover kallsyms, calculate KASLR, generate an exploit target
header, push a binary, invoke a kernel trigger, or modify the device. The prior
CMDQ probe is not repeated.

The exact device remains:

| Field | Value |
|---|---|
| Serial | `G001LT0511550CFT` |
| Model/product | `KFTRWI` / `trona` |
| Build | `Amazon/trona/trona:9/PS7330.4104N/0030099376128:user/amz-p,release-keys` |
| Kernel | `4.4.146+`, arm64 |
| Config evidence | `CONFIG_ARM64=y`, `CONFIG_RT_MUTEXES=y`, `CONFIG_FUTEX=y`, `CONFIG_DEBUG_RT_MUTEXES` not set |
| Runtime hardening observed | `CONFIG_RANDOMIZE_BASE=y`, `CONFIG_ARM64_PAN=y`, `CONFIG_ARM64_SW_TTBR0_PAN=y` |

The configuration is preserved in
`adb/phase5/PHASE5F-CMDQ-RUNTIME-20260803-02/kernel_config.stdout.txt`.

## What the public article establishes

The NebuSec IonStack Part II article identifies GhostLock as
CVE-2026-43499, describes the `remove_waiter()` proxy-path bug, and shows the
fix changing cleanup from `current` to the task associated with the waiter.
It also states that the published exploit details are for generic x86 Linux;
the article explicitly leaves Android adaptation for later work. See the
[article's vulnerability and root-cause sections](https://nebusec.ai/research/ionstack-part-2/).

The article is useful for source-level reasoning, but its GKI-era structure,
CPU-entry-area, KASLR, gadget, and memory-layout assumptions are not evidence
for this arm64 Linux 4.4 tablet.

## Source-level calculation performed

Linux stable v4.4.146 declares `struct rt_mutex_waiter` in
`kernel/locking/rtmutex_common.h`. The pinned declaration has two `rb_node`
members, two pointers, optional debug members, and an `int prio`. The local
source snapshot hash is recorded in
`tools/configs/phase5/linux-v4.4-rtmutex-waiter-layout.json`.

Using the exact device's arm64 pointer size (8 bytes) and the captured config
with `CONFIG_DEBUG_RT_MUTEXES` disabled, the reproducible host calculation is:

| Member | Source-derived offset | Size |
|---|---:|---:|
| `tree_entry` | `0x00` | `0x18` |
| `pi_tree_entry` | `0x18` | `0x18` |
| `task` | `0x30` | `0x08` |
| `lock` | `0x38` | `0x08` |
| `prio` | `0x40` | `0x04` |
| `sizeof(struct rt_mutex_waiter)` | — | `0x48` |

The result is generated by:

```sh
python3 tools/scripts/calculate_phase5_rtmutex_source_layout.py \
  --config adb/phase5/PHASE5F-CMDQ-RUNTIME-20260803-02/kernel_config.stdout.txt \
  --schema tools/configs/phase5/linux-v4.4-rtmutex-waiter-layout.json \
  --pointer-size 8 \
  --output artifacts/phase5/source-layout-review-20260804-01
```

The generated JSON, Markdown table, command record, and SHA-256 manifest are
under `artifacts/phase5/source-layout-review-20260804-01/`.

## What this does and does not prove

### 已證實

- Public source plus an exact ABI/config can calculate compile-time layout
  facts such as the v4.4 `rt_mutex_waiter` member offsets above.
- The device has the v4.4 PI-related `RT_MUTEXES` and `FUTEX` configuration
  enabled, while the captured config does not expose a separate
  `CONFIG_FUTEX_PI` key.
- The upstream v4.4.146 source snapshot contains the pre-fix
  `current->pi_blocked_on` pattern already recorded in Phase 5K.

### 高可信推論

- A source-derived layout calculator is a valid next step for narrowing the
  Android 4.4 structure model, provided every vendor patch, compiler ABI,
  configuration, and conditional field is accounted for.

### 待驗證

- Whether Amazon's PS7330 kernel source exactly matches the upstream v4.4.146
  declaration and whether the vendor tree backported the GhostLock fix.
- The exact compiled offset of `task_struct.pi_blocked_on`; it depends on the
  complete vendor translation unit, all enabled conditional fields, alignment,
  compiler choices, and any Amazon/MediaTek source changes.
- Kernel symbol addresses, KASLR slide, physical-map/CPU-entry-area locations,
  and any function/gadget addresses. These cannot be obtained from public
  source alone.

### 已排除

- The public `auto_extract_offsets` calculator is not an exact-device
  calculator for this result: its reviewed profiles are GKI 6.6/6.12, not
  arm64 Linux 4.4.146.
- The public CyberMeowfia GhostLock source is not a KFTRWI/trona/MT8183 target
  profile.

### 因風險拒絕測試

- Boot/LK extraction through BROM, DA, fastboot, recovery, bootloader unlock,
  or partition access.
- Compiling, pushing, triggering, or adapting a kernel privilege-escalation
  exploit on the tablet.

## Answer to “can public kernel source calculate it?”

Yes, but only in the source/compile-time sense: it can calculate versioned
structure layouts and test whether a source path contains the vulnerable
control flow. It cannot by itself calculate a valid exploit target for this
installed device. That second claim requires an exact matching kernel/boot
artifact or equivalent trusted build output, plus a device-specific analysis;
the current PS7330 boot/vmlinux is still unavailable through the tested shell
boundary.

The next safe research step is an offline comparison of the complete exact
Amazon kernel source/config against the source-derived model. It should not be
followed by exploit execution without a new operation-specific Level 3 report.
